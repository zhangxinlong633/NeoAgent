## 1. 概述

### 1.1 愿景

Neo 定位为**极简、可移植、可扩展**的智能体体系结构。其核心命题为：智能服务的逻辑内核应与具体运行载体解耦，从而在异构算力与资源约束下保持一致的编排语义与能力契约。

目标运行谱系涵盖云计算集群、边缘服务器、工业控制系统，以及资源严重受限的嵌入式装置。部署拓扑由调度层与执行层的组合方式决定，而不绑定特定云厂商运行时或集成开发环境宿主。

### 1.2 设计原则

| 原则 | 规范表述 |
|------|----------|
| 原子性与可组合性 | 功能一律分解为能力原子；原子之间仅通过显式契约协作，禁止隐式全局耦合 |
| 位置透明性 | 业务逻辑不得硬编码执行场所；本地、边缘与云端的选择由调度策略决定（路线图） |
| 计算漂移 | 节点在调度触发前，依据算力、网络、数据位置与成本等因子选择执行场所（路线图） |
| 优雅退化 | 在资源不足或局部失败时，通过降精度、切换实现变体或收缩执行路径维持基本服务可用性 |
| 零信任通信 | 不得假定网络可靠或执行环境可信；跨节点调用须具备超时、重试、可观测失败与熔断语义（路线图） |

### 1.3 目标运行环境

| 环境类别 | 典型装置 | 内存量级 | 算力等级 |
|----------|----------|----------|----------|
| 嵌入式智能装置 | Jetson Nano、RK3588、工业控制器 | 约 512MB–8GB | 中低 |
| 边缘服务器 | ARM64 / x86_64 工控主机 | 约 8GB–64GB | 中 |
| 标准服务器 | x86_64 云主机 | 约 16GB–256GB | 中高 |
| 加速计算集群 | GPU 集群、TPU Pod | 256GB 及以上 | 高 |

本仓库现行实现优先支持**单机部署**：仓库旁路命令行进程内完成 DAG 调度与能力执行。上表界定架构可扩展的目标谱系，而非现行版本的交付清单。

## 2. 体系结构

### 2.0 分层模型

Neo 的逻辑内核划分为两层：**调度层（Scheduler）** 与 **执行层（Executor）**。两层以 **DAG 蓝图** 作为唯一编排契约，既可同进程合设，亦可在后续版本中分布式分设。

与本仓库产品三角的映射关系如下：

| 架构层 | 产品三角对应 | 本仓库主要实现入口 |
|--------|--------------|--------------------|
| 调度层 | DAG（拓扑、依赖、分支与跳过） | `src/dag/dag.c`、`dag_dir.c`；`neo dag run`、`neo plan`、`neo run` |
| 执行层 | Capability Matrix 与 Policy | `src/capability/*`；配置键 `capability_matrix`；目录 `capabilities/` |
| 规划层（可选） | 自然语言至 DAG 的转化 | `src/dag/plan.c`；可省略，直接提交 dags |

### 2.1 调度层

#### 2.1.1 职责

调度层接收并解释 DAG 蓝图，负责节点触发次序、失败处置策略，以及（在路线图中）执行场所决策。

#### 2.1.2 能力清单

| 能力 | 规范说明 | 成熟度 |
|------|----------|--------|
| 依赖解析 | 依据依赖边按拓扑序触发节点 | 已实现（`depends_on`；Kahn 拓扑） |
| 并行控制 | 对无相互依赖的节点实施并发执行 | 路线图（现行以实现拓扑序串行为主） |
| 状态管理 | 节点状态迁移：`PENDING` → `RUNNING` → `SUCCEEDED` / `FAILED` / `SKIPPED` | 进程内已实现；持久化状态为路线图 |
| 位置决策 | 在本地、云端或自动策略间选择执行场所 | 路线图 |
| 异常处置 | 超时重试、失败降级、执行路径切换 | 部分具备（如 `route`、步骤失败返回）；完整策略框架为路线图 |

#### 2.1.3 职责边界

调度层**不得**：

1. 解释或实现能力原子的内部算法；  
2. 替代 Capability Matrix / Policy 判定能力是否允许暴露；  
3. 依赖业务载荷的具体结构，而仅识别节点标识与依赖边。

### 2.2 执行层

#### 2.2.1 职责

执行层登记能力原子、完成路由与调用，并在策略与沙箱约束下产生副作用，将结果回传调度层。

#### 2.2.2 能力清单

| 能力 | 规范说明 | 成熟度 |
|------|----------|--------|
| 能力登记 | 维护可发现能力表及其元数据 | 已实现（矩阵物化） |
| 路由分发 | 按能力名称选择实现并执行 | 已实现（builtin / command / MCP） |
| 资源隔离 | 在进程、容器或 WASM 等边界内执行 | 进程内执行与路径沙箱已实现；容器与 WASM 为路线图 |
| 结果回传 | 向调度层返回执行结果 | 已实现（步骤文本输出） |
| 多态变体 | 同一能力提供多种实现，并按资源条件择优 | 路线图 |

#### 2.2.3 职责边界

执行层**不得**：

1. 编排整图依赖或改写 DAG 拓扑；  
2. 引入与 Capability Matrix 并行的第二套工具命名空间；  
3. 绕过 Policy 暴露未授权能力。

### 2.3 层间接口契约

调度层与执行层通过最小化请求—响应契约交互。下列模式为**目标接口形态**。

#### 2.3.1 调度请求（调度层 → 执行层）

```json5
{
  node_id: "step_3",
  capability: "data.anonymize",
  args: { source: "/tmp/raw.csv", method: "k_anonymity" },
  location: "auto", // 取值：auto | local | cloud；属路线图字段
}
```

#### 2.3.2 执行响应（执行层 → 调度层）

```json5
{
  node_id: "step_3",
  status: "success", // 取值：success | failed | timeout
  output: { cleaned_path: "/tmp/anon.csv", records: 1024 },
  duration_ms: 234,
  error: null, // 失败时填写结构化错误信息
}
```

#### 2.3.3 现行实现说明

现行 DAG 通过 `neo_dispatch_tool` 及大语言模型步骤获得文本输出，并借助 `{{steps.<id>}}`、`{{prev}}` 注入后续步骤。上列结构化状态信封属于演进目标，尚未成为运行时强制协议。

### 2.4 分层依据

| 关注维度 | 调度层 | 执行层 |
|----------|--------|--------|
| 流程编排 | 解析并推进 DAG 依赖 | 不参与 |
| 执行主体 | 决定执行场所（路线图） | 实施具体调用 |
| 故障处理 | 重试、降级与路径切换策略 | 报告本次调用结果 |
| 能力强弱 | 不绑定具体实现 | 维护实现及（未来）多态变体 |

**规范摘要**：调度层负责流程语义，执行层负责能力语义；二者以 DAG 解耦，允许独立演进与分别部署。

## 3. 核心机制

### 3.1 DAG 工作流规范

DAG 为调度层认可的标准编排输入。目标元素集合如下；本仓库以 JSON5 形式的 DAG 对象落地。

| 元素 | 规范说明 | 成熟度 |
|------|----------|--------|
| `nodes` / `steps` | 节点集合；节点引用能力或大语言模型步骤 | 已实现（配置字段为 `steps`） |
| `depends_on` | 节点间依赖关系 | 已实现 |
| `variables` | 工作流级上下文变量 | 路线图（现行部分由模板变量覆盖） |
| `condition` | 条件分支表达式 | 部分由 `route` 覆盖；通用表达式为路线图 |
| `policy` | 图级超时、重试与并行度等策略 | 能力级超时已具备；图级策略为路线图 |
| 选型元数据 | `when`、`when_not`、`requires`、`outcome` 等 | 已实现（供规划目录使用） |

#### 3.1.1 目标语法示例

```json5
{
  nodes: [
    { id: "download", capability: "http.get", args: { url: "https://example.com/data" } },
    { id: "clean", capability: "data.clean", depends_on: ["download"] },
    { id: "analyze", capability: "data.analyze", depends_on: ["clean"] },
    {
      id: "alert",
      capability: "notify.email",
      depends_on: ["analyze"],
      condition: "analyze.output.anomaly == true",
    },
  ],
}
```

#### 3.1.2 现行仓库语法示例

```json5
{
  name: "fetch_then_summarize",
  description: "读取指定文件并生成摘要",
  when: ["需要先读取文件再进行总结"],
  steps: [
    { id: "read", type: "tool", tool: "read_file", args: { path: "README.md" } },
    {
      id: "sum",
      type: "llm",
      tools: "off",
      prompt: "用三句话概括：{{steps.read}}",
      depends_on: ["read"],
    },
  ],
}
```

**命名约束**：步骤字段 `"tools": "on"|"off"` 仅表示该大语言模型步骤是否挂载能力矩阵工具，**禁止**将其更名为 `capability_matrix`。细则见 [`dag.md`](dag.md)。目录化 DAG 由顶层配置 `dag_directory` 指向 `dags/` 加载。

### 3.2 能力矩阵（Capability Matrix）

能力矩阵是执行层的可发现能力登记表：**每一行对应一个能力原子**。稳定标识（现行对外字段为 `name`，目标态可引入全局 `id`）须同时满足下列消费者的一致性要求：反应式工具循环、DAG 中 `type: tool` 的步骤，以及规划器允许名集合。

#### 3.2.1 能力原子字段（目标集合）

| 字段 | 规范说明 | 成熟度 |
|------|----------|--------|
| `id` / `name` | 全局唯一标识 | 已实现（对外 `name`） |
| `description` | 能力说明，用于列表展示与语义匹配 | 已实现 |
| `when` / `when_not` / `tags` / `outcome` | 选型元数据 | 已实现 |
| `schema` / `parameters` | 输入输出的 JSON Schema | 已实现（OpenAI `function.parameters`） |
| `qos_tags` | 资源特征标签（如 cpu_bound、gpu_cuda、io_intensive、realtime） | 路线图 |
| `variants` | 多态实现列表（按优先级排序） | 路线图 |
| `security` | 权限要求与审计级别 | 路线图（路径沙箱与 Policy 开关已提供基础） |

#### 3.2.2 设计要点

同一能力允许存在多种实现变体（例如本地脚本、ONNX、TensorRT、远端应用程序接口）。执行层应根据硬件条件与 Policy，在允许集合中选择合适变体。

配置顶层键优先使用 **`capability_matrix`**；历史键 `tools` 仅作兼容读取。文件化能力包位于 `capabilities/`。用户文档见 [`tool.md`](tool.md)。

**Model Context Protocol（MCP）** 仅作为矩阵的装载器（现行支持 stdio），不得演变为与矩阵并列的第二套工具系统。

### 3.3 执行位置决策（路线图）

节点在触发执行前，调度层应综合评估下列因子：

| 因子 | 说明 |
|------|------|
| 本地算力 | 中央处理器、图形处理器、神经网络处理器等资源的可用程度 |
| 网络时延 | 至远端执行环境的往返时延 |
| 数据引力 | 输入数据已位于本地时，应提高本地执行权重 |
| 能耗约束 | 在电池供电等场景下计入能耗代价 |
| 成本预算 | 远端调用费用是否处于允许区间 |

**决策模型（示意）**：

```
本地得分 = 本地算力可用率 × 数据本地命中率 − 能耗惩罚项
远端得分 = 远端算力预期 × 网络健康度 − 单位成本系数
执行场所 = 在策略约束下对本地得分与远端得分取优
```

**现行实现**：执行默认发生于本机进程（能力沙箱；大语言模型请求可经超文本传输安全协议访问远端）。独立的位置决策子系统尚未实现。

### 3.4 智能降级协议

执行失败或资源不足时，系统应将事件视为降级循环的触发条件，而非直接终止全部编排（目标行为）。

| 层级 | 触发条件 | 处置动作 | 成熟度 |
|------|----------|----------|--------|
| L1 重试 | 单节点超时或瞬时故障 | 有限次重试，并采用指数退避 | 路线图（可由外部编排脚本临时承担） |
| L2 精度降级 | L1 失败或资源不足 | 切换至轻量变体（如 INT8、FP16、输入降采样） | 路线图（依赖 `variants`） |
| L3 路径重规划 | L2 仍失败 | 冻结已完成状态，将上下文提交上层，生成简化后续路径 | 可借助再次执行 `neo plan`；全自动 L3 为路线图 |

**L3 约束**：必须保留已成功节点的输出，仅重规划未完成子图，禁止无差别全量重跑。

### 3.5 检查点与恢复（路线图）

调度层应按可配置间隔持久化执行状态，以支持故障恢复与迁移。

| 项目 | 规范说明 |
|------|----------|
| 断点续传 | 进程异常退出或节点迁移后，自最近检查点恢复 |
| 快照内容 | 已完成节点输出、节点状态、变量上下文、活跃节点集合 |
| 恢复粒度 | 以节点为最小恢复单位 |

**现行实现**：DAG 在单一进程生命周期内执行，不具备跨进程检查点。

## 4. 环境适配

### 4.1 启动期资源自适应（路线图）

系统启动阶段应完成下列步骤：

1. **资源探测**：采集处理器核数、内存容量、加速器存在性及网络状况；  
2. **能力装载**：仅装载满足最低资源门槛的实现变体；  
3. **模式声明**：向管理系统报告运行模式（轻量、标准或高性能）；  
4. **运行期切换**：在资源条件变化时调整模式与已装载变体集合。

**现行实现**：交付物为静态链接的单一可执行文件；能力集合由配置与 Policy 决定，不存在基于硬件探测的变体装载器。

### 4.2 目标部署形态

| 环境 | 调度层 | 执行层 | 通信方式 |
|------|--------|--------|----------|
| 嵌入式（约 512MB–2GB） | 同机轻量调度 | 仅装载匹配硬件的变体 | 进程内调用或共享内存 |
| 边缘服务器 | 同机全功能调度 | 多变体并存并动态路由 | 目标支持 gRPC 或 Unix 域套接字 |
| 云端集群 | 可集群化的集中调度 | 分布式工作节点池 | 目标支持 gRPC 或远程直接访存等 |
| 混合部署 | 边缘调度为主、云端调度为备 | 本地执行与远端卸载相结合 | 目标支持 MQTT 或 gRPC-Web 等 |

**现行仓库形态**：调度与执行位于同一进程；层间交互为函数调用与本地进程执行；大语言模型经超文本传输安全协议访问远端应用程序接口。

## 5. 安全与治理

### 5.1 权限模型

| 目标 | 规范说明 | 成熟度 |
|------|----------|--------|
| 原子级权限 | 能力声明所需权限等级（例如只读、读写、管理） | 路线图；现行 Policy 开关近似控制「是否登记」 |
| 执行时校验 | 调度触发前校验会话权限 | 路线图 |
| 动态授权 | 支持 OAuth2、JWT 或本地令牌 | 路线图 |

**强制约束**：不得为便于演示而默认启用 `shell_enabled`。详见 [`AGENTS.md`](../AGENTS.md)。

### 5.2 审计与追溯

| 目标 | 规范说明 | 成熟度 |
|------|----------|--------|
| 强制审计 | 管理级权限或敏感数据处理必须产生审计记录 | 路线图 |
| 审计内容 | 会话标识、时间戳、能力标识、输入与输出摘要、耗时 | 路线图；现行提供标准错误输出上的步骤日志（`-v`） |
| 审计存储 | 支持消息总线、本地文件或远端对象存储 | 路线图 |

### 5.3 隔离与边界

| 目标 | 规范说明 | 成熟度 |
|------|----------|--------|
| 执行沙箱 | 高风险能力默认在容器或 WASM 中执行 | 路线图 |
| 传输保护 | 跨节点通信默认使用传输层安全 | 路线图（大语言模型的超文本传输安全协议访问已具备传输加密） |
| 路径沙箱 | 读写类能力路径相对于 `capability_matrix.root` | 已实现 |
| 命令白名单 | `commands` 及显式绝对路径必须预先声明 | 已实现 |

身份描述、领域硬约束与答法规范属于 claw 配置块（`soul`、`bootstrap`、`rules`、`memory`），**不得**用能力矩阵替代。原 Skills 子系统已废止。详见 [`claw.md`](claw.md)。

## 6. 规划层（可选）

### 6.1 定位

规划层为**可选组件**，不属于最小可运行内核。

在仅需确定性编排的场景中，应直接提交 DAG（配置内 `dags` 或 `dags/` 目录），无需启用规划层。

### 6.2 职责

当输入为自然语言任务时，规划层负责：

1. 意图理解与任务分解；  
2. 能力检索与匹配（矩阵列表与 DAG 目录；优先输出 `{"use":[...]}`）；  
3. 生成或选用冻结的 DAG 蓝图。

本仓库命令入口：`neo plan`（仅规划）、`neo run`（规划并执行）。

### 6.3 目标部署方式

| 场景 | 规划层部署 |
|------|------------|
| 资源充足 | 本地小型语言模型（约 10 亿至 30 亿参数量级的量化模型），以降低时延 |
| 资源受限 | 远端规划代理；本地仅作意图压缩与结果校验 |
| 网络不可用 | 本地小型模型降级运行；置信不足时向操作者明确提示 |

**现行实现**：规划请求经由配置中的 OpenAI 兼容聊天接口完成，仓库不内嵌小型语言模型运行时。

## 7. 结论

### 7.1 架构价值

| 维度 | 说明 |
|------|------|
| 统一性 | 以同一逻辑内核与 DAG 契约覆盖从嵌入式到加速集群的目标谱系 |
| 灵活性 | 支持执行场所决策、降级与资源自适应（部分为路线图） |
| 简洁性 | 内核限定为调度层与执行层；规划层可裁剪 |
| 可治理性 | 将权限、审计与隔离纳入架构目标；本仓库以 Policy 与沙箱为起点 |

### 7.2 规范定义

**目标定义**：

> Neo＝调度层＋执行层＋（可选）规划层

| 层次 | 职责范畴 | 必要性 |
|------|----------|--------|
| 调度层 | 流程、依赖、异常及（未来）执行场所 | 必要 |
| 执行层 | 能力发现、策略裁剪与实际调用 | 必要 |
| 规划层 | 自然语言到 DAG 的转化 | 可选 |

**本仓库现行定义**：

> Neo＝DAG 执行器＋Capability Matrix＋Policy＋（可选）规划＋claw 提示装配

### 7.3 命名说明

名称 Neo 取「新」与更新之意，强调可在多种环境中扎根的元架构，而非追求单一场景下的能力上限。本项目明确不以「最强集成开发环境智能体」或重型通用工作流平台为产品目标。非目标清单见 [`AGENTS.md`](../AGENTS.md) 第 5 节。

### 8.1 近端演进（基础层，优先于行业/愿景）

下列项支撑 README / [`applications.md`](applications.md) 的「今天就能落地」，**不是**边缘自治或 Agent-as-OS：

| 主题 | 现状 | 说明 |
|------|------|------|
| 步骤可观测 | 已具备 | `-v` 打印 `type` / `tool` / `tools=on\|off`；失败时即使无 `-v` 也打印 `status=fail` |
| Catalog SOP | 已具备 | 如 `show_time`、`repo_pulse`、`workspace_brief`（取数→整理→落盘） |
| 规划选型稳健 | 部分→增强 | 未知 `use` 可解释 + catalog hint；`requires` 预检；可选 `plan.catalog_only` |
| 本地优先约定 | 文档约定 | DAG 中 `type:tool` 走矩阵本地能力，`type:llm` 才调远端模型；完整计算漂移仍为远期 |
| 多路 route / tool retry | 已具备 | `route.cases` 有序多臂；`retry.max` 仅 tool、0..3；仍无 LLM `decide` |
| tool 失败 LLM 热线 | 已具备（默认关） | `dag.on_tool_fail.llm`：本地 retry 耗尽后问 RETRY/ABORT；不改 args、不跳步 |
| 图级重试 / 并行 | 路线图 | 整图重试引擎与并行调度不在近端；失败可由上层脚本或再次 `neo plan` 承担 |

行业层（`capabilities/industry/`、`dags/edge/`）与未来层保持**预留、默认不加载**，见 [`applications.md`](applications.md) §3–4。

工程变更须遵守 [`AGENTS.md`](../AGENTS.md) 所规定的产品三角。本文与实现不一致时，以第 8 章回写结果及用户文档为准。

## 附录 A　术语表

| 术语 | 定义 |
|------|------|
| DAG | 有向无环图；调度层的标准编排输入 |
| 能力原子 | 最小可执行单元，具有明确输入输出契约，对应矩阵中的一行 |
| Capability Matrix | 可发现能力登记表；执行层的权威能力视图 |
| Policy | 在物化或登记阶段裁剪能力可见性及资源上限的规则集合 |
| 计算漂移 | 节点执行前动态选择本地或远端执行场所的过程（路线图） |
| 智能降级 | 在资源受限或执行失败时，通过精度、变体或路径调整维持可用性 |
| 多态变体 | 同一能力原子的多种实现形态（路线图） |
| claw | `soul`、`bootstrap`、`rules`、`memory` 等系统提示装配块 |
